# Changelog

## [Unreleased]

## [v0.3.0] - 2026-09-24

### Features
- **Each stable release can now be projected onto the public GitHub repository, and the public repository is audited against what was published.** `github_release_publish` is a manual job in a new final `publish` stage of the protected stable-tag pipeline, after `release_publish` and in the same `release-publication` resource group. It is manual so a person makes the final call before anything becomes public, and it is not `allow_failure`, so a tag pipeline stays visibly unfinished until the projection has run. It builds one release commit whose tree is the tagged canonical tree, with public `main` as first parent and `rc` as second parent when `rc` carries accepted pull requests, plus an annotated tag, and pushes `main`, `rc`, and the tag in **one atomic, unforced push** -- so an `rc` merged while the job runs rejects the whole push rather than being reset over, and a retry never finds `main` moved without its tag. Only the tagged tree's objects are copied into the scratch repository the job pushes from, so no canonical commit is reachable from anything it publishes. The GitHub Release is created as a draft, the changelog and publication receipt are uploaded and read back by SHA-256, and only then is it published. A retry converges on matching state and fails closed on anything it did not create: an existing public tag is adopted only when the commit and tag object ids are exactly the ones the job would build -- a same-tree tag with any other author, date, message, or tagger is foreign, and receipting it would vouch for objects the job never made -- and a published release with different notes or bytes, a **missing** asset (it was visible without its evidence, so re-attaching it would hide that), an unexpected asset, or a diverged `rc` all stop the job. Neither writing job consumes a job artifact: a manual job can be played long after 30-day artifacts expire, so publication reads only the protected tag and the durable package -- the manifest there exists only if the release contract passed -- and checks the notes against the tagged tree's own changelog section, while withdrawal reads its reason from the immutable yank record. It refuses a yanked version or one older than a release already public, since that would move append-only `main` backwards. Every release's first parent is **anchored to the durable receipts** -- the previous receipted release, or the legacy prefix for the first -- in publication, in adopting an existing tag, and in the audit's walk of the chain, never to whatever public `main` happens to be: building on a commit written to `main` outside the job would have made it permanent, receipted ancestry and cleared the very drift the audit had reported. The one exception to "a yanked version is never published" closes a dead end: if a publication stopped after its push and the version was then yanked, the tag cannot be deleted, so a retry finishes that release as withdrawn -- never as latest -- and writes its receipt, while the withdrawal job fails loudly over a public tag with no published release instead of reporting success. (Closes #76; refs #27, #55.)

  **The outbound host gate is installed, not only specified.** Every path and blob of the tagged tree is checked before anything is fetched, and the commit and tag objects, release body, receipt, and every asset before the first public write, against `CI_SERVER_HOST` and the host component of `CI_REGISTRY`, case-insensitively. A gitlink fails closed, since its content cannot be read. The four deferred evidence documents pass through only as SHA-256 values in the receipt, which is why the registry host they carry by construction never trips it. The public commit and tag are authored, committed, and tagged by `MCKNLY LLC` at the owning account's GitHub noreply address -- public `main` is append-only, so an identity is the one path with no undo -- and every date is the canonical tag's tagger time, so the same release always yields the same public objects and the canonical tagger's identity is never read.

  **The receipt is schema-controlled and deterministic.** `public-release-receipt.json` binds the canonical tag, commit, and tree to the public tag object, commit, tree, and parents, records the qualified image digest with an empty `public_references` list that Docker Hub promotion (#8) will fill without a schema change, and pins the SHA-256 of the changelog and all four deferred evidence documents. It carries no timestamp of its own, so a same-name asset with different bytes can be treated as the conflict it is. It is stored in the release's Generic Package version as well as on the GitHub Release, and the stored copy is what the audit compares against.

  **Withdrawal and drift detection.** `github_release_withdraw` follows `release_yank` automatically on a protected `-yank` tag: it renames the public release with a `[WITHDRAWN]` prefix, prepends the reason, and moves GitHub's "latest" marker to the highest release left -- with `make_latest: "false"` sent explicitly on the rename, because GitHub documents that field as defaulting to true on update and an unqualified rename could hand the withdrawn release the badge -- leaving the tag, commit, and assets as the record of what was published. Like the canonical yank it installs nothing and reads no scan evidence, and it is the one place the host gate withholds rather than fails: a yank reason naming the canonical instance is left out of the public notice, because the yank tag cannot be re-cut and a failed withdrawal would leave the public release looking current. `github_publication_audit` runs alone in scheduled default-branch pipelines -- `validate` now excludes schedules, because a failed scheduled pipeline is the drift alert and a flaky test must not read as one -- and fails when public `main` is not the latest release commit (before the first release: not the legacy prefix), when `rc` does not descend from `main`, when a public tag, branch, or release has no receipt, when a release commit or tag differs from its receipt, when the release commits do not chain through their first parents from the legacy prefix, when a release's name or notes differ from what was published -- a withdrawal notice is rebuilt whole from the durable yank reason, so an edited reason is drift -- when GitHub marks anything but the highest non-withdrawn release as latest, or when a published asset's bytes differ. It declares no environment and reads anonymously, so it can never write to what it audits.

  **The token is scoped by test, not by attention.** `GITHUB_MIRROR_TOKEN` is delivered only to jobs declaring `github-publication`, and `test_only_approved_jobs_receive_scoped_credentials` replaces the Docker Hub-only check with a closed map of every environment to the jobs allowed to declare it -- a new environment name is an unreviewed grant and fails until it is added deliberately. Git receives the token from an askpass helper that reads it from the environment, with global and system configuration disabled, so it never appears in an argument, a remote URL, or a credential store; the REST client never forwards it across a redirect. `scripts/` gains an `__init__.py` so the new `scripts/github_publication.py` and `scripts/release_tools.py` share one import path under `mypy`. `docs/MIRRORING.md` sections 2, 6, 7, and 8 now describe installed state, and section 8 says plainly what a user-owned repository cannot enforce: a ruleset bypass is a role, not a token, so the owner account and its tokens are one writer, and a hand-made write by the owner is caught by the audit rather than prevented. `test_mirror_policy_credentials_match_the_installed_scope` holds section 6 and the pipeline to the same set of token holders.

### Documentation
- **The pre-publication audit is redone against the image itself, layer by layer.** `docs/SANITIZATION_REPORT.md` was dated 2025-10-27 and named three files as its sanitization mechanism that no longer existed; it is replaced, not re-dated. The new audit names its commit (`365d1f4`), pipeline (268), and manifest digest (`sha256:4ae48240…`), and binds them: the commit's immutable full-SHA tag resolves to that digest. The image was checked **per raw layer** as well as merged, because a file a later layer deletes is invisible in the merged view but still ships in every pull. `scripts/image_audit.py` extracts the 20 layers as untrusted data: only regular files and directories are written, and link names, link targets and whiteouts are recorded rather than dropped. Next to them it writes the image manifest and config, which every puller receives. It found the canonical server and registry hosts in **0** of 9,950 files. The scan covered contents, file and directory names, and link names and targets across the layer files, manifest, config and layer record. It also found **0** in the 8,382 merged files. Positive controls on the host-bearing staged SBOM and on a file named after the host prove the scan can find them, and a hit is reported without printing the host. The scan fails closed. It fails when it scanned nothing, when an extraction is missing a metadata file or has a malformed layer record, or when it scanned a different number of files than the extraction wrote. A tree `extract` did not produce is scanned only with an explicit `--no-extraction`. `detect-secrets` 1.5.0 found 22 hits in the tree and 560 in the image, every one read at its line and classified as a placeholder, fixture, checksum, generated identifier, or documentation example. The image's classified set is committed as `security/image-secrets-baseline.json`, keyed by path without the layer number, plugin, and hashed string, so a rebuild can be compared against it. The comparison requires an exact match: it fails on a hit outside the baseline and on a baseline hit the scan no longer reports, so a scan that skipped part of the image cannot pass. It also refuses a scan from another detect-secrets version, plugin set, or filter set, an empty scan, and one sharing no hit with the baseline, because each would under-report and read as clean. A baseline can only be written from a scan whose one regex filter is the metadata exclusion. The secrets scan excludes exactly the three metadata files `extract` writes, which the hostname scan covers; the image config changes every build, so a hit in it could never be classified. The exclusion is recorded among the filters the baseline binds. The license review re-ran on this digest with 0 unresolved and 0 needing review. Because image builds are not reproducible, the report can never name the digest a later release promotes. So it states the allowed delta to the release commit, and `docs/RELEASING.md` gains a scripted pre-tag re-check of the release digest (hostname scan, secrets comparison, and license review, all of which must exit 0), plus a cadence for full re-audits. One finding: uv's build cache (`/root/.cache/uv`, 33 MB) is left in the image. It is not a secret and is tracked in #84, because fixing it changes the image beyond the allowed delta. (Closes #51; refs #28, #84.)

- **The release image's licenses are classified entry by entry, and the obligations of redistributing it are written down.** The release SBOM declared no license for 1,183 of its 1,327 entries, which could not support any statement about license compatibility. `docs/LICENSE_REVIEW.md` records why and resolves every one. 1,038 of the gaps are 519 Rust crates compiled into `uv` and counted once per copy (`uv`, `uvx`); 134 are Go modules compiled into `glab`. Compiled-in dependency metadata names versions, never licenses, so no SBOM tool reading the binary could have filled them. The Debian packages were already almost complete from their copyright files. For the crates, the primary source is **the CycloneDX SBOM uv's own publisher ships inside the image**: exact to the build, inside the audited artifact, and checkable offline. It was cross-checked against crates.io for all 519 crates, and every license agrees; the 25 textual differences are crates.io's legacy `/` separator. Go modules come from deps.dev, and the 12 remaining entries were read by hand from the image, the module source, or upstream, each recording where. `scripts/license_review.py` does the classification, offline and with the standard library only. It first binds the SBOM to the image, because `--digest` alone is only a label. The bytes must match the file hash the registry records for the digest-keyed package, and the SPDX `name` must be the image built from the audited commit. Both arguments are required, and `docs/LICENSE_REVIEW.md` gives the runnable procedure, including checking that the commit's tag resolves to the digest. It exits non-zero while any entry is unresolved or has a license it cannot classify, so a re-run against a later digest cannot report success with entries unaccounted for. It takes the least restrictive branch of an `OR` and the most restrictive part of an `AND`, and every rule fails closed: characters the parser cannot place are rejected, unidentified license text from deps.dev goes to manual review, and a Debian short name counts as permissive only on an exact or `name-` match. The result, for digest `sha256:eed2d103…`: 1,327 resolved, 0 unresolved. Strong copyleft appears only in Debian base-system packages. Weak copyleft is limited to three LGPL Debian libraries and ten MPL-2.0 components compiled into `uv` and `glab`. Every Python dependency is permissive. The document is explicit that the image is an aggregate that MIT does not cover, and it names four obligations, among them a real gap to remediate: `glab` ships with no license notice at all, and `uv` without those of its 518 crates. The source-availability statement is a published pointer to the pinned Debian snapshot, not a source mirror, and is tracked in #54. The missing notices are tracked in #83. Both gate the first Docker Hub push, not the GitHub source publication, because the obligations attach to distributing binaries. The review runs at every release preparation, against the release digest and before tagging (`docs/RELEASING.md`); a CI gate is deferred until a few releases show how often the evidence changes. The SBOM itself is deliberately not enriched: it stays Syft's byte-exact output. (Refs #82, #51, #83.)

- **The canonical hostname is gone from the published tree, and the release-evidence promise it contradicted is withdrawn.** The tree named the private GitLab instance in nine places. Six were mirror-visible only, but two shipped *inside the container image*, in the `gitlab-connect` and `glab-usr` error hints copied to `/usr/local/bin` -- so the host reached every stranger who pulled the image, not only every reader of the GitHub mirror. The host is not a secret and the policy now says so plainly: the `mcknly` GitHub organisation, the `mcknly/robot-dev-team` image, and the canonical namespace path are all public, so the hostname is a short guess from any of them. What removing the literal buys is removal from the automated target lists that work by grep, which is the threat model that actually applies -- calling it secrecy would make `docs/MIRRORING.md` wrong in exactly the way it exists to prevent, and nothing may be built on the assumption. The wrapper hints now name **no** example host at all rather than substituting `gitlab.example.com`, because that string is the exact value both guards exist to reject: the obvious wording would have told an operator to set the one value guaranteed to reproduce the error they were reading. The six documentation sites are all inside shell snippets that already assign to a variable, so placeholders make them better runbooks for anyone operating their own instance; `docs/RELEASING.md` gains a caveat in the one command where the value is load-bearing rather than illustrative, since the SBOM rescan feeds `--source-name` and a document named after the placeholder is rejected on the `release_publish` retry, after the rescan and the manual upload have both already run.

  **Enforcement moved from five files to every tracked file.** The previous check covered the public-surface documents alone, which left unguarded the two places the host actually reached a stranger -- the image-copied wrappers and the operator runbooks -- so both could regress without failing a test. `test_no_tracked_file_names_the_canonical_instance_by_hostname` now reads bytes rather than decoded text, matches case-insensitively, and assembles the needle at runtime so the tree can hold at zero contiguous occurrences *including in the file that enforces it*. It fails rather than skips when git cannot list the tree, and asserts that every tracked path was actually scanned: it is the sole enforcement for the rule now that three subsumed per-file assertions are gone, and a skip or a silently dropped path reads exactly like a pass.

  **The evidence-bytes promise could not survive that rule, so it is withdrawn rather than quietly kept.** `docs/MIRRORING.md` simultaneously promised that the hostname appears nowhere public and that the canonical release manifest, SBOM, vulnerability report, and evaluation are republished as *the same bytes*. Those cannot both hold: `CI_REGISTRY_IMAGE` is registry-host-prefixed and reaches `source_image` and `image_reference` in the manifest, the SPDX `name` that `release_publish` requires the document to carry, the scanned `userInput` and `repoDigests` that bind a Grype report to its digest, and `image_repository` in the evaluation. Each asset carries the host **by construction**, not by oversight, so publishing them unchanged would republish it once per release no matter how thoroughly the tracked tree were scrubbed. The four are now **deferred** until sanitized public variants are designed and tested, with their SHA-256 values pinned in the publication receipt so the canonical bytes stay bound to the release and the gap is a missing artifact rather than an unverifiable claim. What that hash does *not* buy is stated too, because the obvious reading of it is wrong: a canonical SHA-256 checks the canonical bytes only, and a field-aware transformation necessarily produces a different hash, so a sanitized variant needs its own published hash plus provenance metadata naming the canonical hash it derives from. The consumer verification recipe previously routed step 2 through the release manifest -- an instruction to read an unpublished document -- and now runs on the receipt, naming all four deferred assets where it states the gap instead of implying a guarantee. `README.md` carried the same contradiction on the most visible surface in the project, and is corrected in the same change; both it and the unreleased changelog entry above are now held to the policy by cross-document tests, since a release body *is* a changelog section.

  **The outbound host gate is recorded as the contract the publication job must implement**; the publication entry under Features installs it. It fails closed before any public write if a canonical host occurs anywhere in the complete outbound surface: the projected tree, the commit and tag objects, the author, committer, **and tagger** identities on them, the release body, the receipt, and the bytes of every published asset. The identities are called out because they are the path with no undo -- public `main` is append-only, so a release commit stamped with an `@<canonical-host>` address enters the permanent public record one commit per release, and checking the author alone leaves two other paths open. It checks `CI_SERVER_HOST` *and* the host component of `CI_REGISTRY`, since GitLab permits the registry on a separate host and the deferred assets carry the registry host rather than the server one. (Refs #51, #28.)

- **The public source surface exists, ahead of the first public image push.** A public image whose README, docs, and security-reporting path all point at a host nobody outside the project can reach gives a consumer nowhere to verify what they just pulled, so the minimum readable surface lands before the push rather than after it. New `docs/MIRRORING.md` is where that surface lives: what is published and when, the append-only branch and create-only tag rules, credential scoping and rotation, drift ownership and forward-only recovery, and the owner-side setup checklist. It is deliberately in-tree and public rather than an internal note, since a policy a consumer cannot read is not one they can hold the project to. `README.md` carries only a short **source publication note**, beside the documentation index rather than ahead of Quick Start -- repository governance is secondary to understanding and running the project, and leading with it charges every reader for a minority of them.

  Four things the policy states that a reader would otherwise get wrong. **What is read-only is the release line, not the repository**: public `main`, the stable tags, and the release artifacts are written by release automation and nothing else, while `rc`, issues, and pull requests are public intake -- a blanket "read-only mirror" contradicts the same documents' contribution path and is wrong in exactly the place a reader is invited to write. Public history is **one commit per release** on top of an untouched legacy prefix, so the first release commit is a very large diff and is a fast-forward rather than the history rewrite it resembles; `git log --first-parent` there is a release log, and the `--first-parent` matters once a merged pull request makes `rc` a second parent. `sbom/sbom.spdx.json` is a checked-in *reference* document that **can lag the canonical branch**, not the SBOM for any published image -- the authoritative one is digest-keyed and published as a release asset, and a reader finds the in-tree file first. And section 2 now carries the consumer-side check itself rather than only asserting that evidence exists: get the digest you are running, match it against the publication receipt for that release, and tie the source to the image through that same receipt. That recipe is the reachable-verification gap the work was opened for; the operator runbooks describe pull-by-digest but are not written for a public reader. What the recipe cannot cover yet is stated inside it -- the entry below defers the release manifest, SBOM, and scan evidence, and the recipe names all four as a known gap rather than implying a guarantee.

  Section 6 was written as the contract the publication job would implement, and said so rather than describing installed state; the publication entry under Features retires that disclaimer in the same release, and `test_mirror_policy_credentials_match_the_installed_scope` now holds the section and the pipeline to the same set of token holders. Section 7 says that outside the publication job **no public publication happens at all** -- not automatically and not by hand, because the authority model admits no human writer to public `main`, the stable tags, or the release artifacts, so the first public push is the publication job's. Section 5 states what an early intake merge actually costs, which is the ancestry rather than the code: a release commit's tree is the canonical tagged tree, so it omits an unqualified `rc` change on its own and a forward revert undoes the merge before any projection -- the change is never forced to ship, and force-pushing `rc` is not an option the policy offers. The section 1 prohibition on GitHub Actions is scoped to **authority** (build, qualification, tagging, publication) rather than to the word "test", so a future secretless advisory check on a pull request does not contradict published policy. The canonical instance is named by role and never by hostname across the whole surface, which `test_no_tracked_file_names_the_canonical_instance_by_hostname` pins over every tracked file -- the operator runbooks (`docs/CI.md`, `docs/RELEASING.md`) included, per the entry below. (Refs #27, #55.)

- **`SECURITY.md` names a reporting path a stranger can actually use.** It previously directed coordinated disclosure to a GitLab confidential issue on an instance that is not reachable from the internet -- a broken promise that reads exactly like a working one, and the worst place in the surface to have one. Reports now go through GitHub Private Vulnerability Reporting, with the section at the top of the document rather than in its last line. No security email address is published, and the document says so, because a reporter who assumes one exists spends their effort looking for it instead of filing. The guidance asks for the image digest rather than a tag, names the components to attribute a finding to, and says what happens next: the fix is qualified on the canonical instance under the same test, SBOM, and vulnerability gates as any other change, then ships in a normal stable release. Maintainers with canonical access still file confidentially there, and that advice now lives in its own section **after** the reporter-facing one: it is correct for someone who can already reach the instance, and keeping it out of the reporter's region is what lets the guard be strict. Two tests hold the path open. `test_security_policy_names_a_reachable_reporting_path` fails if the old documentation URL returns; `test_security_reporter_section_publishes_one_usable_channel` fails if the reporter's own section acquires a confidential-issue instruction or the private hostname at all -- the same failure restated in prose, which a URL check does not catch. The mirror policy and the release contract are now links rather than inline code, so the reporter who is told to read them can click through. (Refs #55.)

- **The contribution path is split by who can reach the canonical instance.** `docs/CONTRIBUTING.md` previously described only the private GitLab merge-request flow, which is unusable advice for the only people who read it on GitHub. External contributions are welcome through public issues and pull requests, with four properties stated plainly because each of them surprises someone arriving from an ordinary open-source repository: pull requests target `rc` and never `main`, since `main` is written only by release automation and a pull request against it cannot be merged; no CI runs on the pull request, because a second pipeline would be a second opinion on whether a change is fit to release, so the local gates are the contributor's to run; accepted work is replayed onto canonical `main` and qualified there **before** the public merge, since merging to `rc` first would make acceptance irreversible once `rc` becomes a parent of a release commit; and the contributor's own commits stay **reachable** in public history, because `rc` is a second parent of the next release commit. That last promise is stated precisely rather than generously: the commits are reachable under their own authorship, the release commit's tree is still the canonical snapshot, and a first-parent walk and `git blame` attribute the released lines to it. It also depends on a repository setting rather than on the projection -- a squash merge omits the contributor's commits and a rebase merge rewrites their identities -- so the owner checklist now requires merge commits with squash and rebase merging disabled. Commits need a DCO `Signed-off-by` line, and the guide links [Developer Certificate of Origin 1.1](https://developercertificate.org/) rather than paraphrasing it, since the point of the DCO is that a contributor can read what they are certifying; no automated check enforces the trailer, because no CI runs on the pull request, so the guide says a maintainer will not replay a commit without it. The guide also warns that GitHub bases a pull request on the default branch, `main`, with no setting to change that while keeping `main` as the clone default -- so it gives a compare URL whose base is already `rc`, and the owner checklist records that maintainers retarget what arrives against `main`. Also added: `.github/` issue **forms** and a pull request template. Forms rather than legacy markdown templates for a concrete reason -- a markdown template needs its YAML front matter at byte 0, and the header guard requires the license block in the first 12 lines of every tracked markdown file, so the two cannot both hold; in a `.yml` form the header is ordinary `#` comments and the guard is satisfied natively. Blank issues are disabled so no first contact reaches the maintainers without being told what this repository is. The owner checklist orders the two setup steps whose order is load-bearing: Private Vulnerability Reporting is a repository setting and must precede the first public push, because the published `SECURITY.md` names a URL that 404s until it exists, while Issues must follow the first projection, because GitHub reads the chooser from the default branch and Issues enabled earlier are blank issues with no chooser -- the exact path the chooser exists to close. (Refs #27, #55.)

- **The snapshot-enforcement guarantee is now explicitly scoped to the shipped image.** `SECURITY.md`'s "no package can enter the image from outside the frozen archive" describes the runtime image and nothing else. The `validate`, `compat_python_floor`, and `release_contract` jobs run digest-pinned Python images but install `git` from the live Debian mirrors at job time, and that is now a recorded decision rather than an implicit boundary: the image is the only artifact carrying a digest, an SBOM, and digest-keyed scan evidence for a reproducibility claim to bind to, and none of the three jobs contributes a package or a layer to it. The claim stops there on purpose: `release_contract` does declare a release artifact and its `git` output reaches durable release metadata on the yank path, but as validation and an annotated tag message rather than as package contents. Bringing them under `DEBIAN_SNAPSHOT` was declined -- it would put a second home for the timestamp in `.gitlab-ci.yml` and point every merge request at `snapshot.debian.org`, which is materially less available than the CDN-backed mirrors. A bare `git=<version>` pin is worse than either, because Debian prunes superseded binaries and the pin stops resolving at the next point release; a version pin is only resolvable *because* of a snapshot. Removing `git` is not available either: `tests/test_wrappers.py` drives a real git in several places with no skip for its absence, so `docs/CI.md`'s claim that the package was "required by the header guard" was wrong in the exact direction that invites someone to rewrite the header guard and break the suite, and it is corrected. The three jobs now log `git --version`, because that suite tests version-sensitive git behaviour -- credential helper-list reset semantics, host-scoped helper precedence, `rev-parse --git-common-dir` in linked worktrees -- and the job log is otherwise the only place a flipped assertion could be attributed to a git build. `test_apt_consumers_are_scoped_and_record_the_git_build` pins the set of APT-consuming jobs so adding a fourth is a deliberate extension of the boundary -- as `github_release_publish` is, under Features, which uses `git` to write commit and tag objects over an already-fixed tree and so supplies no package contents either. (Closes #65.)

## [v0.2.3] - 2026-09-09

### Features
- **Releases are now gated on a vulnerability scan of the exact digest being published.** A new `security` stage runs checksum-pinned Grype 0.116.1 against an immutable registry digest -- never a rebuild, never a tag -- on protected `main` as a fast fail, and again on a protected release tag with a current database, because vulnerability knowledge is time-dependent and a result that passed when the image was built is not a claim about the day it is released. The tag-time job stages the report and the evaluation under `robot-dev-team-scan/sha256-<hex>/`, and `release_publish` only reads and verifies them: it never runs the scanner, because a Grype report embeds a scan timestamp and a re-derived document would break the durable-file content check on an ordinary retry, with the aliases already moved. The evaluation must bind to the digest from inside the document, come from the pinned scanner, and record a passing database freshness check; anything else fails the release closed in the window before the first alias write. The blocking rule is High or Critical **with an available fix**; unfixed and wont-fix High/Critical are recorded as non-blocking, with the tightening tracked and dated in #60. This is deliberately not `--only-fixed` on the scanner -- the report keeps every match, and only the blocking decision reads fix state, so the evidence for that decision survives the release that accepted it. (Closes #50.)

- **Withdrawal is deliberately not gated.** `release_yank` installs Crane alone, never reads scan evidence, and never invokes the scanner. A gate on that path would make a bad release impossible to pull during an Anchore outage -- or, worse, impossible precisely when the CVE motivating the yank is the finding that fails the scan. The release links are gated on the files existing rather than added unconditionally, so releases published before this landed do not gain permanent 404 links when their assets are reconciled.

- **Exceptions are a reviewed, mechanically enforced file rather than a convention.** `security/vulnerability-exceptions.yaml` scopes every entry to an exact package, version, and type; wildcards and bare vulnerability ids are rejected by the parser, and an id with no artifact scope would otherwise follow the CVE onto any future package. Missing owner, rationale, or expiry is a hard failure, as are expired entries, entries matching no finding, and entries naming a version that is no longer installed -- the way an exception file rots is that entries outlive the findings that justified them and nothing ever fails. It shipped with ten entries covering the CPython findings in #66 and five covering the Go stdlib findings in glab (#71). The CPython ten are gone again in the same unreleased window -- the 3.14 runtime migration below cleared every one of them -- which is the mechanism working: entries are per-CVE and scoped to an exact package version, so they stop matching the moment the artifact moves and the unused-exception rule forces their removal rather than leaving them to rot.

- **The evidence is bound to the report, the policy, and the binary that produced it.** The evaluation records the SHA256 of the report it evaluated, and `release_publish` checks it against the staged document -- the two are published separately and the report is the one a reader opens, so a hand-staged report that disagreed with its evaluation would otherwise be linked from the release as the evidence with nothing detecting it. The recorded grype archive checksum must match the pin, and `policy.sha256` must equal a fingerprint recomputed from the **tag's own** exception file bytes, so an evaluation produced under a different exception file or a different blocking rule cannot be accepted for this release. That last check hashes the file rather than parsing it, which is what keeps it available on a release path that may not import a third-party module.

- **The policy can be checked before it merges.** The gate cannot run on a merge request -- no image is built, so there is no digest to scan -- while the exception file's hygiene rules are hard failures. An MR moving a pinned version could therefore pass every check, merge, and only then break `main` on every entry at once. `release_tools.py evaluate --report <path>` re-runs the policy offline against a report already in hand, with no scanner, network, or credentials. It does not enforce the digest binding or the 48-hour database age, because both describe the evidence rather than the policy and the artifacts it reads are kept for 30 days; the document it writes records that, and the release-side validator rejects it, so a policy-only result cannot be staged as a passing gate. Malformed matches now fail closed too: coercing a missing severity or fix state with `str()` would have turned malformed scanner output into a passing verdict.

- **Expiry is re-checked when evidence is consumed, not only when it is produced.** Scan evidence is keyed by image digest and deliberately reusable, so a later release of the same digest would otherwise pass on an exception that had lapsed in the meantime -- and the new expiry warning would have printed a negative day count while it did. Both the release and the scan job's retry path now reject evidence relying on an expired acceptance. All staged evidence goes through one validator, which also re-parses the staged report and checks that it names the digest being promoted: the recorded hash binds the evaluation to *a* report, and only parsing binds that report to *this* image.

- **The end-of-life base distribution is recorded and printed, not swallowed.** Grype reports that an EOL distribution's vulnerability data may be incomplete, which is the one failure mode a CVE gate cannot detect on its own. It is derived from the report's own distro block rather than scraped from stderr, so it is deterministic and testable. It no longer fires on this image: the trixie migration below landed in the same window, and the Debian 12 entry is retained only so a report taken against an older release still reads correctly.

### Bug fixes
- **Codex installs two binaries again, and a missing companion is now fatal at boot instead of silent at dispatch.** Since 0.147.0 Codex routes every tool call through a separate `codex-code-mode-host` executable that ships as its own GitHub release asset; the `codex-<arch>-unknown-linux-musl` tarball the installer fetches does not contain it. Codex fails **closed** without it, and the shape of that failure is the reason this is worth reading twice: every tool call errors with `failed to spawn code-mode host`, so a dispatch reaches no shell command, never calls `gitlab-connect`, and **still exits 0**. The router records `status=ok`, the mention gets no reply, and the only trace is the run-log -- the quietest failure this system can produce. Because `scripts/install-codex.sh` tracks `releases/latest`, it arrived on the next container boot after 0.147.0 shipped with no change on our side, and any deployment older than this release has had its Codex routes silently disarmed since that boot. The installer now resolves the upstream tag once, stages both executables from that same tag, and replaces the existing pair only when both are ready, so a partial download cannot pair a new CLI with an older host protocol. The companion extracts into its own temporary directory because the codex install's arch-suffixed glob would otherwise match it. Preflight enforcement was widened to match: `# provides:` now declares *every* executable an installer puts on PATH, and `app/preflight.py` requires all of them after the install loop rather than only the harness binaries a route dispatches, so an incomplete harness refuses to boot instead of failing per dispatch.

- **Grype registry authentication binds through the variables Grype actually reads.** The release scan authenticates to the private registry with `GRYPE_REGISTRY_AUTH_*`, not the `SYFT_*` names Grype's own config help prints. `validate_grype_registry_auth()` now gates every live scan on `grype config --load` resolving that authority with non-empty credentials and fails closed otherwise, which also fixes the resolved-config *shape* a version bump must re-verify: `registry.auth` has to render as a mapping list. The guard never logs the resolved document and never lets it reach an exception -- the unreadable-YAML branch raises after leaving the handler, because `from None` clears `__cause__` while leaving PyYAML's quoted source, credentials included, in `__context__`. The registry-free staged-report recovery path skips the guard entirely. (Closes #70.)

### Hardening
- **The five glab Go stdlib findings are accepted explicitly, with an expiry.** `glab` is a static Go binary and Grype attributes stdlib CVEs fixed after its build toolchain to it; upstream has not rebuilt. Rather than leave them unrecorded, `security/vulnerability-exceptions.yaml` carries five entries scoped to the exact `stdlib@go1.26.5` artifact, each with an owner, a rationale, and a `2026-10-26` expiry. The pin (`ARG GLAB_VERSION=1.111.0`, checksum-verified) is what keeps those coordinates from drifting under a release, and the unused-exception rule forces their removal the moment upstream rebuilds -- so this is a dated acceptance, not a permanent waiver. (Refs #71.)

- **`gosu` is gone from the image; `setpriv` from `util-linux` performs the privilege drop.** Debian bookworm builds `gosu` as a static Go binary linked against Go 1.19.8, long EOL, and Grype attributes every Go stdlib CVE fixed after that release to it. There is one root cause and no package-manager remedy: Debian will not rebuild bookworm's `gosu`, so no `DEBIAN_SNAPSHOT` bump reaches it -- #57 confirmed that empirically, `gosu` being the one in-scope-adjacent source that did not move at all -- and no bookworm rebuild ever will. The alternative was annotating it forever: under the exception schema proposed in #50, either one hand-written entry per CVE id all saying the same sentence, or a single class exception permanent by construction. `setpriv` is a C binary with no Go runtime and so no Go-stdlib CVE surface. It is Required-priority and already present, so apt reports 0 newly installed; naming it in the install list is what binds it to the pinned snapshot. Three details of the invocation are load-bearing and are recorded at the call site: the account is resolved **by name** (the remap passes `-o`, permitting a non-unique id, so a numeric lookup could return a colliding account), `--init-groups` is mandatory rather than stylistic (`setpriv` rejects `--regid` without a groups flag), and `--reset-env` must never be added -- it would leave the token loop with nothing to read and fail every dispatch later rather than at boot, and would drop the venv from `PATH` ahead of the preflight. `HOME` is now supplied only by the image's `ENV`; that dependency was previously implicit and is now written down. (Closes #58.)

- **The inheritable capability set is cleared on the drop, and the claim is scoped to what that does.** Measured after the re-exec, `CapInh`, `CapPrm`, `CapEff` and `CapAmb` are already all zero without the flag, because a uid change with no file capabilities and no ambient set empties the inheritable set on its own -- so `--inh-caps=-all` pins the property rather than closing an open hole. It is **not** a bar on regaining privilege. That would be `--no-new-privs` (setuid/setgid bits and file capabilities) and `--bounding-set=-all` (the ceiling itself), both deliberately left out because they change the capability contract inherited by every agent subprocess and every runtime harness installer. `CapBnd` accordingly stays at the Docker default and `NoNewPrivs` stays `0`.

- **The container smoke test can now catch a privilege drop that silently stops happening.** It previously proved only that `/health` answered and that a bad config exited non-zero -- and uvicorn serves `/health` just as well as root, so it would have passed unchanged had the drop disappeared entirely. It now asserts against the *served* process, found by walking `/proc`: all four of the real, effective, saved-set and filesystem ids, the supplementary groups (which distinguishes `--init-groups` from `--clear-groups`), an empty inheritable set, and that `HOME`, the venv-first `PATH` and the agent token all survived the re-exec. This has to be done against the served process specifically, because the image carries no `USER` directive and a bare `docker exec <container> id -u` reports the exec's own root, proving nothing. The positive container now also sets `LOCAL_UID`/`LOCAL_GID` to non-default values: they were previously unset and landed on the build-time `10001`, which the remap would produce by accident, so the assertion was on a default rather than a behaviour. A third case covers a **GID-only** remap, where the uid stays at the build-time default and the entrypoint's `usermod` branch never runs, leaving `groupmod` alone to reconcile both account databases -- relevant because the substitution changed how the primary group is resolved, `gosu` having read the passwd record where `setpriv` resolves the group by name. The two agree only while `/etc/passwd` and `/etc/group` stay consistent, so the test asserts both. The image contract is checked too: `setpriv` present and supplied by `util-linux`, and `gosu` absent from both `PATH` and the dpkg inventory, so a reintroduction cannot be silent.

- **Every pinned dependency carrying a fixable High or Critical advisory has been moved.** The base image goes to `python:3.12.13-slim-bookworm` (re-pinned to its OCI index digest), the Debian snapshot from `20260315T000000Z` to `20260801T000000Z`, `pip` to 26.2, `uv` to 0.12.1, and `glab` to 1.111.0 -- which clears the Go toolchain, `x/crypto`, `x/net`, `x/text`, and the MCP SDK in one step. On the Python side `fastapi` goes to 0.141.1 and `click` to 8.4.2. The base image and `uv` versions are repeated across five `.gitlab-ci.yml` jobs and were moved with the `Dockerfile` so the interpreter that builds a release matches the one it ships. (Refs #57.)

- **The runtime interpreter moves to CPython 3.14.7, clearing every remaining fixable High on the image path.** Ten High CVEs against `python@3.12.13` had no fix on the 3.12 branch when they were accepted, which is why they were the gate's entire day-one exception content. A paired scan on the pinned Grype 0.116.1 -- same scanner, database v6.1.9 built 2026-08-25, `linux/amd64` -- puts the base layer at ten fixable High/Critical findings before the hop and **zero** after, with nothing new introduced. That is better than the three-survivor residue #66 predicted on 3.14.6: the `CVE-2026-15308` backport that missed the `v3.14.6` tag by three weeks is in 3.14.7, and `CVE-2026-11940` / `CVE-2026-11972` turned out to be backported to the maintenance branches after the issue's measurement was taken, so no successor issue is needed and all ten exception entries are deleted rather than re-scoped. The supported floor deliberately stays at `requires-python = ">=3.12"`: 3.14 satisfies it, both install paths use `uv sync --frozen`, and `uv.lock` is byte-identical -- the only interpreter-conditional markers in it are three `typing-extensions ; python_full_version < '3.13'` entries that simply stop applying (the package itself stays installed -- the lock also carries unconditional edges to it, so this is a marker no longer selecting, not a dependency leaving the image). Raising the floor would be a support-policy change and does not belong in a CVE fix. Debian stayed on bookworm for that change so the scan delta remained attributable to one axis; the distro axis moved separately in #59, below. (Closes #66.)

- **`starlette` is now a direct, exactly pinned dependency at 1.3.1**, up from 0.52.1 resolved transitively. FastAPI 0.141.1 still floors it at only `>=0.46.0`, so the FastAPI bump alone would not have held the fixes for CVE-2026-54283 (form limits silently ignored) or CVE-2026-48818 (SSRF via UNC paths in `StaticFiles`). It was already a de facto direct dependency -- `app/api/dashboard.py` imports `WebSocketDisconnect` from it -- so the pin also corrects a declaration that had only ever been transitive. Neither advisory looks reachable in this deployment: nothing mounts `StaticFiles` and the webhook surface is JSON rather than form-encoded.

- **The Debian snapshot pin is now enforced rather than merely configured.** The base image ships its own deb822 source pointing at the live `deb.debian.org` mirrors, and APT reads `sources.list.d/` in addition to `sources.list` -- so writing snapshot entries without clearing that directory left both active and the pin governing nothing. APT selects the highest version across all sources, so any package the live mirror published ahead of the frozen archive would have entered the image silently, and the newly added `apt-get upgrade` step widened that exposure from the packages we name to every upgradeable base package. The build now clears the directory first and then asserts, from `apt-get indextargets`, that every active Debian index URI is under `snapshot.debian.org`. The assertion is on that property and not on the known filename, so a base-image layout change cannot quietly reintroduce a live mirror. No shipped image was affected: at the time of the fix the live mirrors and the snapshot agreed on every candidate version.

- **The build now fails when `apt-get upgrade` holds a package back.** `upgrade` never installs or removes packages, so an update whose new version needs a new dependency is skipped and the command still exits 0 -- a security fix could disappear from a rebuild with no signal anywhere. The build parses the `N not upgraded` count and refuses to continue when it is non-zero. The check fails closed: the simulation is captured before parsing so a failing `apt-get` is caught rather than read as a broken pipe, the parse runs under `LC_ALL=C`, and a count that is empty or not entirely digits fails the build rather than defaulting to zero -- a guard that read its own failure as "nothing held back" would reproduce the silent-skip bug it exists to catch. `upgrade` was kept over `dist-upgrade` deliberately, so the resolver still cannot add or remove packages unattended. The step also runs under `DEBIAN_FRONTEND=noninteractive` with `--force-confold`, and the inert `--no-install-recommends` was dropped from it.

- **The compatibility-floor lane is pinned to current 3.12 security maintenance and scoped away from tag pipelines.** It was introduced on `python:3.12.13-slim-bookworm`, one 3.12 security release behind on the day it landed -- and six of the ten CPython findings the runtime hop cleared name `3.12.14` as a fix version, so the lane meant to prove the floor still works would have run CI on an interpreter carrying them. It now pins `python:3.12.14-slim-bookworm` (index `sha256:0f5b26b9...`, confirmed to be what `3.12-slim-bookworm` resolves to). The distinction that makes this maintainable is written down in `docs/DEPENDENCY_MANAGEMENT.md`: the lane's **minor** is the support policy and moves only with `requires-python`, its **patch** is a security number and moves on its own. The lane also carries `rules:` limiting it to merge requests and default-branch pushes. Nothing `needs:` it, and the release jobs are `needs:`-driven, so on a `v*` tag it could never have blocked `release_publish` or `release_yank` -- but it could have turned a tag pipeline red after the release had already published, and spent a full `pytest` run on `rdt-validate` in the middle of a yank.

- **The container base moves from Debian 12 (bookworm, end-of-life) to Debian 13 (trixie).** `PYTHON_IMAGE` goes to `python:3.14.7-slim-trixie` (index `sha256:656d12e7...`) with no interpreter movement -- the trixie image carries the same `PYTHON_VERSION=3.14.7`, so this is a one-axis distro change and `uv.lock` is untouched. The three snapshot suites become `trixie`, `trixie-updates`, and `trixie-security`, and `DEBIAN_SNAPSHOT` moves from `20260801T000000Z` to `20260901T082454Z`. That second move is not cosmetic: the snapshot was twenty-four days *older* than the bookworm base image it was pinned against, which is the silent version of a stale pin -- when the frozen archive predates the base, `apt-get upgrade` has no candidates for the preinstalled debs, the held-back guard reads `0 not upgraded` and passes, and the step covers nothing while appearing to work. The six runtime `.gitlab-ci.yml` literals move with the `Dockerfile`, and `compat_python_floor` re-pins to `python:3.12.14-slim-trixie` -- its *minor* still follows `requires-python` and its *patch* still follows 3.12 security maintenance, but its *distro* follows the runtime, because a codename encodes nothing about the support floor and leaving that lane on bookworm would keep exactly the condition this change ends. (Closes #59.)

- **What the migration actually cleared, measured rather than assumed.** Paired scan, pinned Grype 0.116.1, one frozen database (v6.1.9, built `2026-09-01T06:32:09Z`), `linux/amd64`, both images built `--no-cache` from the same tree: total matches **399 -> 285**, deb matches **384 -> 270**, image size 366 MB -> 385 MB, 125 -> 124 packages. Fixable Medium deb findings went **14 -> 0**. The five blocking High findings are identical in both images and are not deb at all -- they are the Go stdlib findings in `glab` already accepted under #71 -- so `evaluate` returns `verdict=pass blocking=0 excepted=5` on the candidate, and the EOL warning that fires on the bookworm report does not fire on the trixie one. The number the issue expected to move did **not**: unfixed High/Critical debs are **102 -> 103**. That bucket is nearly the same CVEs re-attributed to renamed packages (`libcurl4` -> `libcurl4t64`, `perl-modules-5.36` -> `perl-modules-5.40`), 45 carried over verbatim, and it is still dominated by perl, curl, libssh2, and glibc entries Debian has not issued a fix for. So the honest framing is the inverse of the issue's: on an EOL distro that residue is permanent by construction, while on a supported one it is a live queue that will surface as *fixable* -- and therefore blocking -- as Debian issues DSAs. The migration did not shrink the residue; it made the residue mean something, and it moved the maintenance burden from writing exceptions to keeping `DEBIAN_SNAPSHOT` current.

- **The transition guards were exercised, not relaxed.** Trixie ships APT 3.0.3, and the held-back parser is anchored to the exact sentence `N not upgraded.` -- it still parses, verified in the migration build, and the fail-closed branch is unchanged. `apt-get indextargets` under APT 3.x still reports every active index under `snapshot.debian.org`, so the source assertion holds across the deb822 layout the trixie base ships. `gosu` remains absent: trixie does build it on a current Go toolchain, but `setpriv` carries no Go runtime at all, which is the property that does not decay as a toolchain ages, and `scripts/ci-smoke-image.sh` continues to assert gosu's absence from both `PATH` and dpkg. `util-linux` moves 2.38.1 -> 2.41.5 and `util-linux-extra` is gone from the image; `setpriv` is still supplied by `util-linux` itself, and all four privilege-drop smoke cases pass.

- **Every shipped harness was re-verified on the new glibc and OpenSSL, not assumed forward-compatible.** glibc moves 2.36 -> 2.41 and OpenSSL 3.0 -> 3.5.7, and the second one is the coupling that matters: the official Python image builds CPython against the distro libssl, so the service's own TLS stack changed with the base. Checked directly -- `ssl.OPENSSL_VERSION` reports `OpenSSL 3.5.7`, and an authenticated `GET /api/v4/version` against the GitLab instance from the image's own Python returns 200. All seven installers succeed and all seven harnesses dispatch: Claude Code 2.1.252, Antigravity `agy` 1.1.23, Codex 0.152.0 (with its paired `codex-code-mode-host`, exercised by a dispatch that performs a real shell tool call rather than `--version`, since a missing companion fails closed at exit 0), OpenCode 1.18.25, Goose 1.48.0 against the host-served model through `host.docker.internal`, Grok 1.0.13 on the argv prompt path with `--no-auto-update`, and Pi 0.84.4 on its pinned user-local Node v22.23.1. `gitlab-connect` was exercised end to end on Debian's newer Git (2.39 -> 2.47.3), including a real clone and fetch through `glab-usr`'s host-scoped credential-helper reset -- a green `glab --version` proves nothing about that path, and `glab` carries its own Go TLS so it proves nothing about the Python side either.

### Testing
- **The repeated Python image pin is now a contract rather than a convention, and the supported floor is executed.** That pin appears in the `Dockerfile` and six `.gitlab-ci.yml` literals across seven consumers -- `.security_scan` is a hidden template extended by both scan jobs, so enumerating job keys is precisely how a reference gets missed -- and nothing previously failed when one copy was left behind. `test_runtime_python_image_pins_agree` scans the raw file for fully qualified `python:X.Y.Z-slim-<codename>@sha256:` pins and requires every one to equal the `Dockerfile`'s, with a single deliberate exclusion. That exclusion is the new `compat_python_floor` job, which runs a frozen sync plus `pytest` on the floor interpreter so `requires-python`, `README.md`, and `docs/AGENT_ONBOARDING.md` stop advertising a version nothing executes; the test also requires that lane's series to equal the declared floor, so the two cannot drift apart. A second test, `test_python_exceptions_are_scoped_to_the_runtime_interpreter`, requires every `python` exception's `version` to match the interpreter the `Dockerfile` ships. Neither the image build nor the scan runs on a merge request, so without it a runtime hop that forgot to re-scope a surviving entry would go green, merge, and only then break `main` on the unused-exception rule.

- **The pin contract rejects a wrong-*shape* reference, not just a wrong-*value* one.** `test_runtime_python_image_pins_agree` originally collected by the fully qualified pin pattern, which made it an allowlist: `image: python:3.14.7-slim-bookworm` with the digest dropped, or the floating `python:3.14-slim-bookworm@sha256:...`, was never collected at all, so it could not reach the equality check and the test passed. Collection is now on the bare `python:` token and every hit must be fully qualified, which inverts the default from "an unrecognized shape is ignored" to "an unrecognized shape must be justified" -- the same inversion the raw-text scan already makes over parsed job keys, one level further down. Failures now carry line numbers, so a job left behind on the floor's exact pin names the job that was missed rather than the floor. The floor lane's pin is also read from inside that job's own block: the previous unbounded search ran on into the next job when the lane declared no usable image and reported "the floor is running the runtime pin" for a lane that declared no pin at all. `test_python_exceptions_are_scoped_to_the_runtime_interpreter` is scoped to `type: binary`, the type the interpreter findings carry.

- **The dashboard websocket endpoint has direct coverage for the first time.** `/dashboard/ws` backs the only module in `app/` that imports starlette directly, and it was previously exercised by nothing -- the smoke test only polls `/health`. Two tests now cover a live subscription streaming a broadcast frame and unsubscribing cleanly on disconnect, and the disabled-feature path closing the socket with code 1008. Both were checked against deliberate regressions of the code they cover.

- **The committed SBOM is bound to the pin it describes.** `sbom/sbom.spdx.json` had gone stale across a full runtime hop and nothing noticed: `scripts/header_guard.py` skips `sbom/`, and no check read the document, so the reference artifact advertised `python 3.12.13` -- the interpreter carrying the ten CPython CVEs the hop existed to clear -- long after the image stopped shipping it. `test_reference_sbom_records_the_runtime_interpreter` now requires the document's `python` package to equal the version parsed out of the `Dockerfile`'s `PYTHON_IMAGE`, turning step 3 of the update checklist from a remembered step into a mechanical one, in the same shape as the two pin-contract tests beside it. The binding is scoped to the interpreter on purpose rather than compared byte for byte: regeneration needs a Docker daemon, and Syft stamps a per-run `documentNamespace` and timestamp, so the document is not reproducible from the tree. The artifact itself is regenerated from the trixie image with the pinned Syft v1.42.2 (1332 -> 1328 packages, `python 3.14.7`, `openssl 3.5.7-1~deb13u2`). The release path was never affected -- `sbom_publish` stages the smoke-tested image's own bytes and `publish_release()` copies exactly those -- so this governs the checked-in reference copy only. (Closes #73.)

- **The APT suites and the base image can no longer drift apart silently.** They are two independent literals describing one Debian release, and a mismatch does not fail any build step: APT installs the named packages from the frozen archive perfectly happily, and the result is a mixed image nothing downstream flags. `test_apt_suites_match_the_base_image_codename` requires the three suites to be `<codename>`, `<codename>-updates`, and `<codename>-security` for the codename in `PYTHON_IMAGE`. The `Dockerfile`'s existing `apt-get indextargets` assertion does not cover this -- it governs where indexes come from, not which release they describe -- and the likelier direction of drift is a base bumped to a new codename with the suites left behind, since the base pin moves on a security cadence while the suites move only on a distro migration.

- **The floor lane's distro is now bound to the runtime's, the same way its minor is bound to `requires-python`.** `compat_python_floor` is deliberately excluded from the runtime pin equality set, and until now that exclusion was total: the lane's codename was constrained in neither direction, so a distro hop could move the `Dockerfile`, the six `.gitlab-ci.yml` literals, and the APT suites while leaving the floor lane behind on an end-of-life Debian -- exactly the condition #59 exists to end, reintroduced on the one job nobody rebuilds locally. This migration had to move that literal by hand, which is the demonstration. `test_runtime_python_image_pins_agree` now requires the floor pin's codename to equal the runtime's while continuing to require its version to differ: the version axes encode a support policy and keep their own schedules, the codename encodes nothing about the floor.

- **The reference SBOM is bound to the base image's Debian release, not only to its interpreter.** The interpreter binding added above cannot see a distro-only hop: this release keeps `PYTHON_VERSION=3.14.7` across the bookworm -> trixie move, so an SBOM left on the old image would have satisfied it verbatim while describing 125 packages the image no longer ships. `test_reference_sbom_records_the_base_image_distro` reads the `distro` qualifier off the document's own deb purls (`pkg:deb/debian/base-files@13.8%2Bdeb13u6?arch=amd64&distro=debian-13`), which Syft derives from the image's /etc/os-release rather than from anything this repository states, and requires every one of them to name the release `PYTHON_IMAGE` is built on. The codename-to-major hop goes through a small table in the test module; an unmapped codename is a hard failure with the line to add, never a silently skipped check.

- **The EOL-distro tests no longer depend on the shipped runtime being the end-of-life case.** The default `scan_report()` fixture moves to Debian 13.6, which is what the trixie image actually reports, so the ~35 evaluator tests that call `evaluate()` now exercise the supported-distro path. `test_eol_distro_is_recorded_rather_than_swallowed` passes an explicit Debian 12 report instead, which is the case that has to keep working after the migration: scan evidence is digest-keyed and outlives the image it describes, so a yank or a forensic re-evaluation can still hand the evaluator a bookworm report. `test_supported_distro_is_not_flagged` correspondingly asserts the whole distro block and the absence of the warning from the printed summary, rather than only the boolean.

### Documentation
- **`docs/DEPENDENCY_MANAGEMENT.md` records what the APT snapshot actually guarantees.** A snapshot timestamp at or after the base image's build date only prevents pinning an archive older than the image; it does not guarantee the upgrade step has candidates, and on a freshly bumped base image it normally has none. The guidance now says to measure what a build resolves rather than assume a package count, and to compare against the base image the same build uses -- attributing a base-image bump's updates to the upgrade step overstates what that step does. The update checklist now names every file a version pin is repeated in, and the `fastapi`/`starlette` pin coupling is written down with its maintenance cost.

- **Vulnerability scan counts must now be reported with their input, and the canonical input is settled.** Grype returns materially different results for an image than for that image's own Syft SBOM -- measured on one Grype v0.116.1 binary and one database built 2026-08-04, against a pre-#58 image, 381 matches versus 458 and 12 fixable High/Critical versus 49. The cause is Go symbol reachability: Grype captures Go function symbols when it catalogs an image itself and discards matches whose vulnerable symbols the compiled binary does not use, while SPDX has no field for that evidence, so an SBOM input silently falls back to coarser module-granularity Go matching. Scanning is therefore defined against the image digest and the SPDX SBOM remains an inventory and provenance artifact rather than a scanner input; the image result is a strict subset whose entire delta is matches the symbol-aware path judged unreachable. The docs require quoting the image identity, scanner version, database build date, and input form alongside any count. (Closes #61.)

- **`docs/DEPENDENCY_MANAGEMENT.md` records the two things that make a snapshot bump go wrong on a codename change.** First, `debian` and `debian-security` are imported independently and the security archive normally lags by hours, so a timestamp new enough to sit after the base image's build date is often ahead of the newest security snapshot -- and because `snapshot.debian.org` resolves a request to the latest snapshot at or before it, a timestamp ahead of an archive's newest import can silently start resolving elsewhere once that archive catches up. The guidance is now to prefer an exact timestamp that already exists in the listing and to record what all three suites resolved to at pin time, since the value in the `Dockerfile` is a request rather than a statement about what was installed. Second, both fail-closed guards fire loudly on a codename change by design, and the doc says what to do instead of relaxing them: re-anchor the held-back parser if a future APT changes the summary wording, and add the newly-named package or move the snapshot when a library transition holds an upgrade back -- never `dist-upgrade`.

- **The doc also states what a deb finding means now that the base distro is supported.** The direction is the opposite of the intuitive one: on an EOL distro Debian stops issuing fixed-versions, so High/Critical debs surface as `not-fixed`/`wont-fix` and are recorded rather than blocking; on a supported distro the same class carries a fixed-version as soon as one exists, and the blocking rule is High/Critical *with an available fix*. The migration therefore converted a permanently-ignored bucket into a live one, which is what makes the one-month snapshot cadence load-bearing rather than tidy, and it is why the `EOL_DISTRO_RELEASES` entry for Debian 12 is retained rather than deleted. `SECURITY.md` and `docs/SYSTEM_DESIGN.md` state the correct base distro.

## [v0.2.2] - 2026-07-31

### Features
- **Every stable release now carries a durable SBOM tied to the exact image digest it publishes.** The SPDX SBOM was a 30-day artifact of the `build_smoke_publish` job and nothing else, so a published digest had no retrievable SBOM once that artifact expired. A new `sbom_publish` job stages the SBOM built from the smoke-tested image in the Generic Package Registry under `robot-dev-team-sbom/sha256-<hex>/sbom.spdx.json`, and `release_publish` copies those exact bytes to `robot-dev-team-release/X.Y.Z/sbom.spdx.json` and links them from the GitLab Release alongside `release-manifest.json` and `changelog.md`. The release fetches and validates the staged SBOM after resolving the source digest but before the first alias write, so a missing or malformed one fails the release closed with nothing mutated. Nothing is ever regenerated: Syft embeds a per-run namespace and timestamp, so only passing the built bytes through keeps a pipeline retry a no-op instead of a content conflict. Both ends also require the document to name the image it is filed under, so the digest binding is a property of the content and not just of the package path. `CI_JOB_TOKEN` only -- no new credential or trust boundary, and the upload runs on the protected-ref runner that already carries every other durable release write. Consumers, retrieval paths, and the manual recovery for a digest built before this existed are documented in `docs/RELEASING.md`. (Closes #49.)

  **Applies to releases published after this change.** `v0.2.0` and `v0.2.1` have no SBOM package file and are deliberately not backfilled; their release records are unchanged, and yanking one of them does not add a link to a file that is not there.

### Documentation
- **`docs/RELEASING.md` now states that container image aliases carry no `v` prefix.** The `v` belongs only to the Git tag and the changelog heading that mirrors it, while `pyproject.toml`, the image aliases, and the Generic Package version are all bare `X.Y.Z`. The alias table was already correct but never said so, and the post-publication verification step asked operators to reconcile a "version tag" without saying which namespace it meant. This is a real trap during release verification: querying a `v`-prefixed image alias returns a registry `not found` that is indistinguishable from "this release was never published", so a malformed query reads as a failed release. A new table maps every artifact, including the full-SHA image alias -- a bare 40-character commit SHA, where the widely used `sha-<short>` guess misses in exactly the same way -- and the verification step now names each one explicitly. No automation in this repository writes a `v`-prefixed image alias, so such a lookup cannot resolve to anything this project published; it says nothing about the registry as a whole, and a `vX.Y.Z` alias that does resolve is out-of-band drift that must not be trusted as release evidence.
- **`docker-compose.release.yml` is now gitignored, and named in `docs/RELEASING.md`.** A host-specific override selecting a digest-pinned release image names a registry and a deployment-specific digest, so it should not reach the public repo. It sat neither tracked nor ignored, one `git add .` from being committed. Documenting the filename next to the `image_reference` guidance keeps the next operator from inventing a different name that the ignore rule does not cover.

## [v0.2.0] - 2026-07-27

### Breaking changes
- **Startup now fails on an under-credentialed route.** The container runs a preflight (`python -m app.preflight`) before installing any harness, and **refuses to boot** when an enabled route dispatches an agent that has no GitLab token or no git identity -- a route that could never have worked. Previously such routes sat dead and harmless until a webhook fired, then failed confusingly inside `glab-usr` mid-dispatch.

  **Who this affects:** the shipped `config/routes.yaml` wires `claude`, `gemini`, and `codex`. A deployment running only some of them with the other tokens blank booted fine before, and will now stop with an error naming the agent, the exact env vars expected, and the routes to fix.

  **To upgrade:** either credential every agent your routes name (`<AGENT>_AGENT_GITLAB_TOKEN` plus a non-placeholder `<AGENT>_AGENT_GIT_EMAIL`), or delete the routes for agents you do not run. There is no escape-hatch flag -- the config must be correct. Run `python -m app.preflight` locally to see exactly what would fail. The reverse case stays permissive: a token with no route is only a warning, so staged rollouts and `BRANCH_PRUNING_AGENT` identities keep working. See `docs/ENVIRONMENT.md`.

  Startup is also now fatal on the other ways a config can be unusable: a `ROUTE_CONFIG_PATH` that does not exist (previously treated as an empty route list, so a typo booted an inert container), a config yielding no dispatchable agent tasks at all, a route giving an agent an empty `command:`, and -- checked *after* the install loop -- a required harness binary that is not on PATH. That last one closes the other half of the invariant: a failed download or a mis-declared `# provides:` line used to leave a container that started fine and then died at `exec` on every dispatch.
- **Scalar `author` matching is now case-insensitive.** Previously, `author: "Cavin"` required an exact-case match against the event author; it now matches `cavin`, `CAVIN`, etc., aligning with how `mentions` and `assignees` already behave and removing a footgun where the scalar and list forms behaved differently. GitLab usernames are case-insensitive server-side so real-world breakage is highly unlikely, but operators who relied on scalar `author` as a case-sensitive filter should review their routes. Empty-string `author` values (scalar `""` or empty list entries) are now rejected at load time -- omit the field instead to allow any author.
- **The Gemini harness and model contract changed.** Local `config/routes.local.yaml` overrides must change the Gemini command from `gemini` to `agy`, pass `--dangerously-skip-permissions`, preserve the `--model ${GEMINI_MODEL}` pair, and hand the prompt through `-p "${PROMPT}"`. The shipped model defaults are now `CLAUDE_MODEL=claude-opus-5`, `GEMINI_MODEL=gemini-3.6-flash-high`, and `CODEX_MODEL=gpt-5.6-sol`. Antigravity 1.1.5 and newer accept stable slugs from `agy models`; an unrecognized value aborts with exit 1 and prints the models available to that account. The slug needs no quoting. Older Antigravity builds require the friendly-name form, although newer builds retain that form for compatibility.

### Features
- **Assign on issue creation** -- creating an issue with an agent already assigned now dispatches that agent's read-write `assign_work` route immediately, instead of first running a read-only triage/review pass. GitLab sends an `Issue Hook` with `action: open` when the assignee is populated at creation; the shipped `assign-issue-*` routes now match `action: ["open", "update"]` and sit **above** `issue-triage`, so first-match-wins routing hits the assign route. This is deliberately either/or: a pre-assigned agent skips triage and goes straight to work. It also fixes a confusing prior interaction -- with `ENABLE_AUTO_UNASSIGN=true`, a create-with-assignee issue was routed to read-only triage and then had its operator-set assignee silently removed once triage finished, even though `assign_work` never ran. Controlled by the new `ENABLE_ASSIGN_ON_ISSUE_CREATION` env var (default `true`); set it to `false` to revert creation events to triage. Scope is issues only -- an MR opened with an assignee still goes through `default-merge-request` review. The `match.action` field now accepts a list as well as a scalar (see `docs/ROUTES.md`). **Local overrides:** operators running a `routes.local.yaml` (`ROUTE_CONFIG_PATH`) must apply the same reorder + action-list change to their copy. (Closes #31.)
- **Panel-aware multi-agent reviews** -- issue and merge-request review prompts now frame serial reviewers as a panel. Later agents read the existing discussion, lead with net-new findings, endorse or disagree with earlier conclusions concisely, and avoid inventing low-value differences merely to appear novel. The strategy depends on the queue's serial dispatch order and is covered by prompt-rendering regression tests. (Closes #3.)
- **Randomized multi-agent dispatch** -- routes can set `randomize: true` to shuffle a copy of their agent list without mutating configured order. Expanded `@all`/`@agents` work can be shuffled independently with `RANDOMIZE_ALL_MENTIONS` (default `true`), while an explicit list such as `@claude @gemini @codex` stays deterministic. The selected order remains in structured logs for incident replay. (Closes #2, #14.)
- **Pi harness support (optional, disabled by default)** -- adds a commented `pi-nemotron` route for `@earendil-works/pi-coding-agent`, using OpenRouter and the bind-mounted `~/.pi/agent` configuration. Because Pi requires Node >=22.19 while the base image remains Node-free, `scripts/install-pi.sh` downloads a checksum-verified, user-local Node 22 only when a Pi route is enabled and credentialed. The route disables approvals and session persistence, accepts the prompt on stdin, and ships with a long inactivity allowance for the default Nemotron model. (Closes #32.)
- **Grok Build harness support (optional, disabled by default)** -- `scripts/install-grok.sh` plus commented `grok` routes, `.env.example` block, and `docker-compose.yml` mount. Unlike the provider-agnostic harnesses, one `grok` binary backs exactly one logical agent, so the agent slug, the GitLab username, and the env prefix are all plain `grok` (`GROK_MODEL`, `GROK_AGENT_*`). Two things about the CLI are worth knowing before wiring it: (1) **grok never reads stdin** -- its headless flag `-p` / `--single` takes the prompt as the flag's *value*, so the routes pass the `${PROMPT}` argv placeholder exactly as the `gemini`/`agy` routes do. Its `--prompt-file` flag accepts `/dev/stdin` and looks like a way onto the unbounded stdin path; it works when you test it from a shell, and fails on every real dispatch with `Failed to read '/dev/stdin': No such device or address (ENXIO)`, because a shell redirect hands the CLI a *file* on fd 0 while the dispatcher hands it a *pipe* and closes the write end once the prompt is written -- and grok re-opens fd 0 *by path*, so the kernel is asked to reopen a pipe with no writer. (`grok agent stdio` is a JSON-RPC server for the SDKs, not a prompt-on-stdin mode.) Argv transport means prompts are capped at 128 KiB and visible to process inspection during the run. And (2) in the default `plain` output format Grok prints its reply only when the run finishes, so a long stretch of tool calls produces no stdout to reset the inactivity watchdog -- the routes ship `max_inactivity_seconds: 1800`, and `--output-format streaming-json` is the fallback if that is not enough. Auth is the host's `~/.grok/auth.json` (written by `grok login`), bind-mounted read-write like the Claude/Gemini/Codex config dirs; there is no `XAI_API_KEY` path, and `GROK_DEPLOYMENT_KEY` covers headless hosts with no browser. The installer fetches the release artifact directly rather than piping xAI's `install.sh`, which in a container would symlink a bare `agent` command onto `PATH`, append a block to `~/.bashrc`, and stage downloads inside the bind-mounted `~/.grok`. The routes pass `--no-auto-update` for the same reason the installer avoids that script: it is *not* a version pin (the installer still fetches latest on every container start), but grok's self-updater stages into `~/.grok/downloads` and repoints `~/.grok/bin/{grok,agent}`, so a container-side update would leave a ~150 MB binary in the operator's home directory and flip the symlink their **host** grok resolves through, to a version the container chose. (Closes #18.)
- **Goose harness support (optional, disabled by default)** -- `scripts/install-goose.sh` plus commented `goose` routes, `.env.example` block, and `docker-compose.yml` mount. Goose is the reference example for a harness driving a model served on the host (llama.cpp, Ollama, LM Studio, vLLM): configure it on the host, bind-mount `~/.config/goose`, and provider/model/extensions/credentials carry into the container unchanged. The one value that cannot carry is a `base_url` on loopback -- correct on the host, but inside the container `127.0.0.1` is the container -- so the config is mounted **read-only** at a staging path and `app/goose_config.py` materializes a container-local copy at startup with loopback hosts redirected at `host.docker.internal` (already provided by `extra_hosts`; no Docker network to join, and the host's own config is never modified). No `GOOSE_PROVIDER` / `OPENAI_HOST` / API-key variables: only the four standard BYOA vars. Both endpoint spellings Goose accepts are rewritten -- a full `base_url` URL and a bare `*_HOST` value with no scheme (`OLLAMA_HOST: localhost:11434`). The materialization refuses to run if its target is a mount point (which would make it delete the host's config rather than copy it) or if the mounted source has no `config.yaml`, and it warns when an enabled `stdio` extension names an executable the image does not ship -- the mount carries extension config, not the executables it names. Note the model server must be reachable from the Docker host gateway (bind it to `0.0.0.0`, not `127.0.0.1`), and the commented routes ship `max_inactivity_seconds: 1800` because a local model can go silent during a long prefill and only stdout resets the watchdog. (Closes #13.)
- **Harness installs are now filtered by configuration** -- `docker-entrypoint.sh` no longer runs every `scripts/install-*.sh` unconditionally. A harness is installed only when some enabled route runs its binary *and* that agent is credentialed, so an unused agent stops costing a binary download at every start. Each install script declares what it puts on PATH with a `# provides: <binary>` line (needed because the script name is not the binary name: `install-gemini.sh` installs `agy`), and the gate keys off that binary rather than the agent name -- so the single `opencode` binary installs when *any* `opencode-*` agent is enabled. Deleting an agent's routes is now a genuine opt-out. A route command that no installer provides is assumed to be already on PATH (BYOA) and is never fatal. Note that `scripts/` is baked into the image, so changes need `docker compose up --build`. (Closes #20.)
- **Multi-author routes** -- the `author` field in `config/routes.yaml` now accepts either a single username (existing behavior) or a list of usernames so a single rule can authorize multiple GitLab operators without per-user duplication. See `docs/ROUTES.md` for the schema and examples.
- **`gitlab-connect issue list` and `mr list`** -- thin pass-throughs to `glab issue list` / `glab mr list` that preserve `--repo` injection on read-only mounts. Flags such as `--source-branch`, `--state`, `--author`, `--label` are forwarded verbatim. Unblocks the "check for existing MR before opening" step in the GitLab workflow. The `ls` alias also normalizes to `list`.

### Bug fixes
- **Timed-out agents are auto-unassigned when configured.** Wall-clock and inactivity timeouts now use the same cleanup contract as successful and manually killed runs: when `ENABLE_AUTO_UNASSIGN=true` and the timed-out agent is the assigned agent, RDT unassigns it once and records self-unassign suppression so the echo webhook cannot retrigger the failed work. Timeout notification failure does not prevent the cleanup. (Closes #1.)
- **Submodule-only drift no longer creates destructive backup branches.** Branch resolution distinguishes ordinary dirty files from a changed submodule gitlink. A submodule-only mismatch is logged and skipped instead of committing a "backup" that would rewind the submodule; mixed changes and uncertain git failures still take the conservative backup path. (Closes #15.)
- **Pushes were attributed to the wrong agent when a global credential helper existed.** Git queries credential helpers in configuration order (system, then global, then repository-local) and the lists *accumulate*, so the repository-local `credential.helper` that `glab-usr` wrote never displaced a global one -- the operator's global helper answered first. If it had an entry for the GitLab host, every push and pipeline trigger was recorded under that identity no matter which agent had just been authenticated, while `glab-usr` reported success and the commits carried the correct author. Observed on `feature/issue-25-gitlab-ci`, where Codex-authored commits produced Grok push events. `glab-usr` now writes a host-scoped `credential.<protocol>://<host>.helper` key whose first value is empty; git treats that as a helper-list reset, discarding inherited helpers for `GLAB_HOST` only, so the selected agent's store is the sole responder and helpers for every other host are untouched. The key is built from `GLAB_PROTOCOL` and from `GLAB_HOST` including any port, because a https-scoped key does not match an `http` request and a portless key does not match `host:8080`. **Note the intended consequence:** there is no longer a fallback for `GLAB_HOST` -- a missing or stale store is now a hard auth failure rather than a silent wrong-identity push, and a failure to configure the helper aborts instead of warning and reporting success. `gitlab-connect` inherits the fix. See `docs/AGENT_ONBOARDING.md`. (Closes #40.)
- **`glab-usr`'s global fallback destroyed credentials for other hosts.** When no writable repository was available (read-only project mount, or invocation outside a checkout), the fallback wrote a single line to `~/.git-credentials` with mode `w` -- git's *shared* default store -- silently deleting every entry for any other host on each dispatch. Because all agents share `appuser`'s home, one such invocation cleared the store for everyone, and the loss only surfaced later at an unrelated `git` operation. The fallback now uses a dedicated per-host store at `~/.config/glab-cli/git-credentials-<host>`; `~/.git-credentials` is no longer read or written. This also fixes a second defect on the same path: the old single-value `git config --global credential.helper` failed outright with `cannot overwrite multiple values with a single value` when a multi-valued `credential.helper` was already configured, after which `glab-usr` printed only a warning and still reported authentication success, leaving the caller to authenticate as whatever the pre-existing helper returned. Credential files remain mode `0600`. (Closes #42.)
- **Branch pruning could operate under a dispatched agent's identity.** `BranchPruner` authenticates once per pass with no working directory -- the global credential path -- and then runs its `fetch --prune` and `push origin --delete` with the working directory set to each project. Because git reads repository config *last*, the host-scoped helper a dispatched agent leaves in a checkout discards the pruner's global one and answers in its place, so a live pass would delete branches under the wrong agent's audit identity or fail where that agent lacks the pruning agent's permissions. (Found in review of the fix above, which introduced the repository-scoped key that makes local config outrank global here; pruning defaults to disabled with `BRANCH_PRUNING_DRY_RUN=true`, so a default deployment was never exposed.) The pruner now pins every git command with command-line `-c` overrides -- the only scope above repository config -- rather than re-authenticating inside each repository, which would rewrite `.git/config` and `.git/credentials` underneath any agent still running there (`git_auth_lock` is released before an agent's CLI starts, so it does not protect that window). `glab-usr` publishes the key and shell-quoted helper it configured on stderr as a `CREDENTIAL-CONFIG` line, so the four key-construction constraints stay in one place instead of being re-derived in Python where a mismatch would fail silently. If that line is absent, the pruning cycle is skipped rather than run under an unknown identity. The pruner also now authenticates from a throwaway empty directory instead of inheriting the process working directory, so `glab-usr` takes its global path deterministically: in the container the cwd is the app directory, but under `./launch-uvicorn-dev` it is a real checkout that may itself be a pruning target, and the background service would have written credentials and git identity into it.
- **Worktree and submodule checkouts silently took the global credential path.** `glab-usr` decided between repository and global scope by testing whether `.git` was a writable *directory*. In a linked worktree or a submodule `.git` is a **file** holding a `gitdir:` pointer, so both shapes failed the test and fell through to the global path from inside a perfectly writable checkout -- writing the host-scoped helper *and* the git identity into `~/.gitconfig`, where they apply to every repository under that home rather than the one being worked in. On a workstation that persistently removes the operator's own credential helper for `GLAB_HOST`. Both `glab-usr` sites now resolve the checkout with `git rev-parse --git-common-dir` and derive the store from that, which handles plain checkouts, linked worktrees (common dir = the parent repository's `.git`) and submodules (`<parent>/.git/modules/<name>`) uniformly; ordinary checkouts are unaffected, since their common dir is `<repo>/.git`. The `safe.directory` walk-up that must run *before* any git-native resolution -- on an ownership-mismatched mount `rev-parse` fails the dubious-ownership check before it can report a path -- now recognizes the `.git` file shapes too, instead of climbing past the worktree to some unrelated ancestor. **Scope note:** because `git config --local` from a linked worktree writes the repository's *common* config, the credential and identity are shared by every sibling worktree; one agent per repository is an invariant, worktrees included, and is now asserted by a test rather than left implicit. Per-worktree isolation would require enabling `extensions.worktreeConfig` on the operator's repository for a concurrency guarantee the shared `~/.config/glab-cli` state does not provide anyway. No shipped route dispatches into a worktree or submodule, so this was latent rather than live. See `docs/AGENT_ONBOARDING.md`. (Closes #43.)
- **A read-only dispatch's credential configuration can be inert, and now says so.** `docker-compose.yml` exposes the same project tree read-write and read-only, so a read-only dispatch reads the `.git/config` a writable dispatch wrote. Its global helper is therefore outranked in that checkout and never consulted, which the `configured global credential store` line alone reported as success. `glab-usr` now warns, naming the repository and the helper that will answer instead. Deliberately a warning rather than a failure: the read-only path cannot push, and `glab`/`gitlab-connect` authenticate from `GLAB_TOKEN` rather than the git helper, so failing would break every read-only dispatch over an identity those dispatches never use.
- **Gemini dispatch delivered an empty prompt to `agy` (every run since the Antigravity swap failed).** The dispatcher writes the rendered prompt to the agent's stdin, but Antigravity has no stdin mode -- `-p` / `--print` takes the prompt as the flag's *value*, so `agy` received the route's literal `""` and exited with `Error: empty prompt` before doing any work. Routes can now place a `${PROMPT}` token in `args`; the dispatcher substitutes the rendered prompt into that argv slot and skips the stdin write for that agent. The shipped gemini routes use it (`-p "${PROMPT}"`). Agents whose CLI does read stdin (claude, codex, opencode) are unchanged. Oversized prompts (>128 KiB, the Linux single-argument cap) now fail with an actionable run-log error instead of an opaque `E2BIG`. The `${PROMPT}` token must be its own complete argv element; partial forms such as `-p=${PROMPT}` are rejected at route-load time. See `docs/ROUTES.md`; found while verifying #19.
- **Wrapper credentials now key on `GLAB_HOST` instead of `GLAB_API_HOST`.** When the web and API hosts differ (e.g. local-dev GitLab on a non-standard port), `glab-usr` previously wrote git credentials keyed to the API host, leaving `git push`/`pull` against the web host unauthenticated. Single-host deployments are unaffected.
- **`gitlab-connect` `--repo` injection no longer leaks the origin host.** In read-only mounts, the `--repo` flag now resolves to `owner/project` only (no host prefix), letting `glab` route the call to the currently-authenticated host. Fixes failures when the container's `origin` remote uses a service name or internal port that does not match `GLAB_HOST`.
- **`config/routes.yaml` documented the inactivity watchdog wrong.** The header comment claimed `max_inactivity_seconds` resets on "stdout/stderr output"; the implementation has always been stdout-only (stderr is tracked for diagnostics but deliberately does not stay the timeout, so a retry loop -- which produces only stderr -- cannot hold the queue open). `.env.example` already said so; the two now agree. Comment-only, no behavior change, but it would have misled exactly the person tuning a slow route.

### Hardening
- **Literal mentions no longer dispatch agents.** Mention parsing strips inline and fenced code, blockquotes (including GitLab multiline quotes), and indented code before expanding usernames. Agent-authored `@all`/`@agents` is suppressed, an agent's self-mention is filtered, and route-level `author` matching remains the final authorization check. This prevents quoted examples and copied conversations from fanning out work while preserving explicit live mentions. (Closes #14, #16; refs #17.)
- **Loud-fail on placeholder `GLAB_HOST` and `*_AGENT_GIT_EMAIL`.** Both wrappers now refuse to run when `GLAB_HOST` resolves to `gitlab.example.com` (with or without an explicit port), and `glab-usr` refuses to authenticate when the agent's `*_AGENT_GIT_EMAIL` is unset and would fall back to `<agent>@example.com`. Replaces silent misconfiguration with an immediate, actionable error. Note: the email check fires on every `glab-usr` invocation including read-only paths (e.g. `gitlab-connect issue view`); set `*_AGENT_GIT_EMAIL` for every configured agent in `.env`.
- **Input validation** in `glab-usr`: rejects `GLAB_PROTOCOL` outside `http`/`https`, and rejects schemes embedded in `GLAB_HOST` / `GLAB_API_HOST`.
- **More informative missing-token error** -- names both the expected env var (e.g. `CLAUDE_AGENT_GITLAB_TOKEN`) and the token file path the script looked for.
- **`glab-usr` self-defense against root-owned `~/.config`.** A stray `docker compose exec app ...` (which defaults to root) that invokes `glab` or `gitlab-connect` will create `/home/appuser/.config/glab-cli/`, `/home/appuser/.gitconfig`, and similar files owned by root, poisoning every subsequent appuser-driven agent dispatch with a cryptic `permission denied`. `glab-usr` now detects the condition up-front and emits an actionable remediation. The guard covers both directories (`~/.config`, `~/.config/glab-cli` -- writability and searchability) and files (`~/.config/glab-cli/config.yml`, `~/.gitconfig`, and the per-host global store `~/.config/glab-cli/git-credentials-<host>` -- it tracks whichever file `glab-usr` actually writes, which is no longer `~/.git-credentials`; see the global-fallback fix under Bug fixes). Writability tests are routed through `$BASE_USER` so root callers don't bypass the check via Unix permission-ignore semantics. The container entrypoint's recursive chown is also documented as defensive against this scenario (it heals on container restart). When testing the wrappers from inside a running container, always pass `-u appuser` to `docker compose exec`.

### Infrastructure
- **GitLab CI image workflow** -- merge requests run Ruff, mypy, the header guard, and the full pytest suite on a project-locked validation runner. Protected `main` pipelines build one `linux/amd64` image with rootless Docker-in-Docker, exercise successful startup and strict-preflight rejection against that exact image, generate an SPDX SBOM with digest-pinned Syft, and publish only an immutable full-commit-SHA registry tag. The pipeline rejects an existing SHA tag and records the raw registry manifest digest in retained artifacts using a parser compatible with the pinned Buildx version. See `docs/CI.md`. (Closes #25.)
- **Protected stable release promotion** -- annotated protected `vX.Y.Z` tags now validate against
  `pyproject.toml`, the dated changelog section, and `main` ancestry before promoting the existing
  full-SHA image digest to `X.Y.Z`, `X.Y`, `X`, and `latest` aliases. The release job never
  rebuilds the image, verifies every registry alias, stores a durable manifest and changelog in the
  Generic Package Registry, and creates the GitLab Release. Publication is serialized and
  idempotent. Annotated protected `vX.Y.Z-yank` tags authorize withdrawal, record the actual job
  user, and recompute each moving alias from compatible non-yanked releases. See
  `docs/RELEASING.md`. (Closes #26.)
- **OpenCode harness (optional, disabled by default)** -- adds an `opencode` agent CLI with the `opencode-kimi` identity, six route entries, and host config bind mounts that ship commented in `.env.example`, `config/routes.yaml`, and `docker-compose.yml`. Uncomment the blocks and set `OPENCODE_KIMI_AGENT_*` env vars to enable; the preflight then pulls in `scripts/install-opencode.sh` (while disabled, the binary is skipped -- see #20). See `docs/ADDING_AN_AGENT.md` for the worked example. (See #4.)
- **Gemini harness swap** -- replaced the deprecated `@google/gemini-cli` npm
  package with Google's Antigravity CLI (binary: `agy`) for the `gemini`
  agent. The agent identity is unchanged across env vars, route `agent`
  fields, GitLab account, and the `~/.gemini` bind mount; only the
  `command:` field in `config/routes.yaml` and the install script body
  point at the new harness (see issue #10).
- **Node.js / npm removed from the base image** -- the Dockerfile Node.js block, `NODE_VERSION` build arg, npm cache and global-prefix plumbing in `docker-entrypoint.sh`, the `./npm-cache` bind mount, the `NPM_CACHE_DIR` env var, and the old Gemini CLI's `procps` dependency have been dropped. The optional Pi installer is the sole exception: it bootstraps a pinned, user-local Node 22 only when Pi is enabled. Operators can delete the former host-side `npm-cache/` directory after pulling.

### Operator-facing changes
- **Antigravity OAuth bootstrap.** On any new host, run a one-time OAuth
  bootstrap so the `gemini` agent's container has a credential to use:
  ```
  docker compose run --rm app agy
  ```
  The default entrypoint runs the UID/GID remap and the install scripts
  before exec'ing `agy` as `appuser`, so the resulting credential file
  is owned by the same UID that normal webhook dispatch uses. Do **not**
  override `--entrypoint` -- bypassing it produces a root-owned token
  file that the unprivileged webhook process cannot read.
  Complete the Google sign-in in your browser when `agy` prints the
  URL. `agy` writes its OAuth credential to
  `~/.gemini/antigravity-cli/antigravity-oauth-token` (mode 0600). The
  existing `~/.gemini` bind mount makes that file visible on the host
  filesystem too, so future container starts and rebuilds inherit it
  automatically. If you authenticate `agy` on a host with a full
  desktop session, the token may land in libsecret instead of in the
  file; on such hosts, run the bootstrap above to also create the file
  for container use. See `docs/AGENT_ONBOARDING.md` for details.
- **Gemini preflight.** `app/services/agents.py` now fast-fails the
  gemini agent (before invoking `agy`) when the credential file is
  missing, unreadable, empty, or not valid JSON. Operators see a clear
  "Antigravity is not bootstrapped" message instead of a 30-second
  OAuth-callback timeout. Claude and Codex agents are unaffected.

### Features
- **On-demand project cloning** (`ENABLE_AUTO_CLONE`) -- projects are cloned automatically on first webhook trigger with namespace-aware paths and concurrent-clone protection.
- **Automatic branch resolution** (`ENABLE_BRANCH_SWITCH`) -- detects and checks out the relevant branch from the webhook payload before agent dispatch, with divergence handling and backup branch creation.
- **Smart branch selection** (`ENABLE_SMART_BRANCH_SELECTION`) -- uses `closes_issues` API and note mentions to rank linked MRs when resolving branches for issues, preventing false-positive branch switches.

- **Auto-unassign** (`ENABLE_AUTO_UNASSIGN`) -- automatically unassigns agents after successful task completion or manual kill, using `--assignee '-agent'` to preserve other assignees.

- **Kill-path enhancements** -- dashboard kill switch now posts a termination comment and auto-unassigns the killed agent.
